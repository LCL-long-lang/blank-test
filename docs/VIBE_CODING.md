# 这个项目是怎么用 Vibe Coding 做出来的

本文记录 NL2SQL ChatBI 从一句需求到上线的完整过程。整个项目的代码基本都由 AI 编程助手（Claude Code）写出，人没有逐行写代码，但每个阶段都做了方向决策和验收。

## 什么是这里说的 Vibe Coding

| 角色 | 做什么 |
|---|---|
| 人 | 提需求、选技术栈、确定开发顺序、看结果、提出“不对 / 再改”、决定什么时候进入下一步 |
| AI | 调研方案、写设计文档、拆阶段、写代码和测试、运行验证、定位问题并修复、汇报结果 |

它和“让 AI 随便写”的区别，靠三条约束来保证：

1. **先写文档，再写代码。** 每次动手前，AI 先给出设计或计划，人确认后才实现。
2. **每个阶段都有可运行的验收基线**，包括 pytest、vitest、评测脚本和端到端测试。“做完了”的标准是测试通过，而不是 AI 说做完了。
3. **模块相对独立。** 出了问题只改一个模块，不允许大面积返工。这一条是人在项目中途明确提出的，后面成了硬约束。

## 过程时间线

### 第 0 步：调研（只问不做）

**人的输入：**

> 需求：智能数据分析系统。1. 接入大模型 2. 能够操作数据库，基于用户的自然语言查询数据库返回最终的结果 3. 需要在前端实时渲染查询出来的可视化图表。请详细设计底层架构：可以采用哪些核心技术、有哪些企业常用的 Agent 框架、有哪些开源项目可以参考、前后端技术栈建议如何设计。

**AI 的输出：**
- 核心技术清单：Text-to-SQL、Schema Linking、RAG、自我纠错、结构化输出、语义层、MCP、评测体系。
- 框架对比：LangGraph、LangChain、LlamaIndex 等。
- 开源参考：WrenAI、Vanna、DB-GPT、SQLBot。
- 一条贯穿全项目的原则：**LLM 只负责“想”，代码负责“做”**。

这一步没有写任何代码。

### 第 1 步：定技术栈，出模块规划

**人的输入：** 指定阿里云百炼 Qwen3、LangChain + FastAPI、SQLite3、React；后端要有会话管理和上下文记忆；前端三栏布局，左边聊天管理、中间问答、右边图表。

**AI 先问了 4 个问题再动手：**

| 问题 | 人的选择 |
|---|---|
| 交付形式 | 先写模块规划文档，不写代码 |
| 业务数据来源 | 生成电商示例库 |
| 图表库 | ECharts |
| 之前那份写了一半的架构文档 | 删除，以新规划为准 |

**AI 的输出：** [DESIGN.md](DESIGN.md)，包括分层架构、11 个后端模块、数据库表、REST 和 SSE 接口、前端组件树和状态管理、核心时序。

### 第 2 步：拆阶段，并在中途调整顺序

AI 最初的拆法是“框架 → 前端（用 Mock）→ 后端 → 联调”，前后端可以并行开发。

**人的调整：**

> 把后端开发放在 phase2，前端开发放在 phase3，先开发后端，然后开发前端，最后再联调。每一个 phase 都比较独立，方便后续改错修正，防止系统大面积修改。

AI 按这个顺序改了文档，并补了一节“模块独立性约束”：
- 单向依赖，下层不能引用上层。
- LLM 和数据库连接从外部传入，测试时可以换成假的。
- 能写成纯函数的尽量写成纯函数。
- 每个模块配一个测试文件。
- 接口格式只在一个地方定义。

后面每个阶段都按这些规则执行。

### Phase 1：搭框架，跑通“Hello World”

AI 搭好了两端的工程骨架、电商示例库（2 万订单、24 个月，带 618、双 11 的季节性）、接口格式定义和健康检查。

**过程中的问题：**
- **装不上依赖。** 本机的系统代理会断开 pip 的连接。AI 改用阿里云镜像并绕过代理，没有改用户的系统设置。
- **模型名不可用。** 人提供 API Key 后让 AI 验收。AI 发现 `qwen3-max` 返回 404，就查询了这个账号能用的模型列表，改成 `qwen3.8-max` / `qwen3.8-flash`，并验证了关闭思考模式和流式输出都正常。

**验收：** pytest 10 个、vitest 3 个测试通过，`/api/health` 显示三项都就绪，Qwen3 能连通。

### Phase 2：后端，从底层往上一层层做

按依赖顺序做了 9 步：数据层 → SQL 安全 → 图表 → Agent 管道 → 数据仓储 → 会话 → 记忆 → 流式问答 → 评测。每一步都只依赖已经测试通过的下层模块。

两个值得一提的做法：
- **假 LLM 测试。** 单元测试用按顺序返回预设回答的假模型，所以 134 个测试都不消耗 Token，还能精确覆盖“第一次 SQL 报错、第二次修正成功”“连续 3 次失败”这类分支。
- **意图识别和图表推荐不用结构化输出。** AI 判断百炼兼容接口对结构化输出的支持不确定，改成让模型只输出一个词或一段 JSON，再由代码解析。这样兼容性更好，也方便用假模型测试。

**评测驱动调 Prompt：**

| 改动 | EX（关闭 Few-shot） |
|---|---|
| 第一版 | 47.6% |
| 加入业务约定（“近 N 个月”按自然月算、占比类返回数量、多系列用长表、比率按订单去重）；评分改成“列子集匹配” | 81.0% |
| 开启 Few-shot | 85.7% |

一半的失败来自评分太严格（比如多返回一列也算错），另一半是问题本身有歧义（比如“近 6 个月”算不算本月）。前者改评分方式，后者写进 Prompt 的业务约定，不针对单道题打补丁。

**验收：** 134 个测试通过；用 curl 看到完整的事件流；追问改写正确；中途断开连接后，消息被标记为 `cancelled`。

### Phase 3：前端，要求“有科技感”

**人的输入：** 开始 phase3 的制作，要求 UI 有科技感，任务完成后测试 phase3 的任务完成情况。

**AI 的做法：**
- **风格：** 深海军蓝底、青色辉光、细网格背景、玻璃面板、带四角框的图表画框、生成中显示扫描线。
- **配色先校验再用：** 图表的 8 个系列色用色板校验脚本检查了色弱区分度和对比度，全部通过后才使用，没有靠肉眼判断。
- **后端不改：** 前端统一调整后端给的图表配置的外观（线宽、柱宽、坐标轴、提示框），不碰数据，后端一行没改。
- **安全渲染：** 模型输出的 Markdown 和 SQL 高亮都由自写的轻量解析器转成 React 节点，不使用 `innerHTML`。

**测试以外，还在真实浏览器里走查了一遍，发现了两个单元测试看不出来的问题：**

| 现象 | 原因 | 为什么测试没发现 |
|---|---|---|
| 浏览器里图表完全不显示 | `echarts-for-react/lib/core` 是 CommonJS，在浏览器里默认导出变成了一个对象 | 测试里把图表组件换成了占位组件 |
| 图表框只占半屏，下面一大片空白 | 外层容器的高度没有传到图表框 | jsdom 不计算布局 |

**验收：** vitest 42 个测试通过；在真实浏览器里接 Mock 和真实后端各走了一遍，控制台都没有报错。

### Phase 4：联调

AI 写了两个可以反复运行的脚本：
- `check-contract.mjs`：用后端的 `/openapi.json` 对比前端的 TS 类型，结果是 11 个模型、9 种 SSE 事件字段全部一致。
- `run-e2e.mjs`：用 Puppeteer 驱动真实浏览器，接真实后端和真实模型，跑 8 个规划用例加 2 个补充用例。每个用例既检查页面，也调接口核对后端存下的数据。

**联调发现的问题都是真实的产品问题：**

| 问题 | 怎么发现的 | 修复 |
|---|---|---|
| 追问“只看手机数码，按区域对比”画成了折线图 | 用例 2 失败 | 改写和生成 SQL 的 Prompt 里明确：新的维度替换旧的维度，只按问题里提到的维度分组 |
| 追问之后再问“各会员等级的客户占比”，被套上了上一轮的筛选条件 | **用例 3 通过了，但截图里的答案数字不对** | 改写前先判断这是追问还是新问题，新问题原样处理；同时在测试里加了这项检查 |
| 刷新页面后回到欢迎页 | 用例 8 | 用 localStorage 记住当前会话 |
| 前端时间比后端早 8 小时 | 走查时发现会话分组不对 | 前端时间从 UTC 改成本地时间 |

第二个问题最能说明“看结果”的价值：测试只检查了图表类型是不是饼图，是人工看截图时才发现数据口径不对。

**验收：** 10 个用例全部通过；首个事件最慢 125 ms；回答完成最慢 7.0 秒（目标 8 秒）；控制台没有报错。

### 上线后的小调整

- 本机 5173 端口被另一个项目占用（后端日志里出现了本项目没有的 `/api/conversations` 请求），前端改用 3000 端口，同时改了跨域配置和测试。
- 加了 `启动.bat`，双击就能启动前后端并打开浏览器。

## 关键决策

| 决策 | 理由 |
|---|---|
| 用显式的固定流程，不用自由的 ReAct Agent | NL2SQL 的步骤是固定的；固定流程更可控、好调试，每一步都能单独推给前端 |
| 两个 SQLite 文件，业务库只读 | 模型生成的 SQL 物理上碰不到会话数据，也改不了任何数据 |
| 模型只输出图表类型，图表配置由代码组装 | 前端拿到的配置一定能渲染，切换图表类型时不需要再调模型 |
| 明细数据不回传给模型 | 避免模型编造数字，也控制 Token 消耗 |
| 前后端字段统一用 snake_case | 前端类型和后端模型一一对应，联调时不需要做名称转换 |
| 先后端后前端 | 人的决定。前端开发时可以直接对着真实接口调试 |

## 值得复用的做法

1. **先定接口格式。** Phase 1 就把接口和事件格式定成两端共享的类型，后面三个阶段都按它对接，最后的字段核对结果是 0 处不一致。
2. **每个阶段留一条测试基线。** 后面出问题时，先跑前面阶段的测试，就能判断是哪一层坏了。
3. **假 LLM 让测试免费且确定。** 单元测试不调真实模型，真实模型只在评测和端到端测试里用。
4. **单元测试和真实浏览器走查都要做。** jsdom 发现不了模块格式问题和布局问题。
5. **用评测数字指导 Prompt 调整。** 每次改 Prompt 都重跑 EX；一次分数下降时先复测两次，确认是不是模型随机波动，再决定要不要回退。
6. **人要看结果，不能只看“通过”。** 测试只能检查写进断言的东西。

## 可以直接复用的指令

按顺序发给 AI 编程助手即可，括号里是本项目的实际选择：

1. 我要做 [智能数据分析系统]，必须实现 [...]。请先设计底层架构：核心技术、框架选型、可参考的开源项目、技术栈。不要写代码。
2. 技术栈定为 [Qwen3 + LangChain + FastAPI + SQLite + React]，后端要有 [会话管理、上下文记忆]，前端布局是 [三栏]。请做系统模块规划。
3. 请拆成 phase：先搭前后端基础框架并运行测试 → 后端接口 → 前端 UI → 联调。每个 phase 相对独立，出错时只改一个模块。
4. 开始 phase N，完成后运行测试，告诉我验收结果。
5. 开始联调，结束时做端到端测试，发现问题先修再汇报。
